## Stress-path contract check (brief items → verdict)

- **Probe/merge errors propagate fail-closed as designed:** YES — no catch between `send()` and the route; REST → 500, MCP → `isError`. Documented in contract §3 tier-1 (`docs/CONTRACT.md:226-227`). Right choice for a write: no silent duplicate, no silent skip of merge; retry is safe because the substring guard makes merge idempotent.
- **`updateMemoryContent` = ONE atomic writeBatch:** YES, one batch/one send — but server-side atomicity is an assumption, not a verified fact → **F-01** (the half-merged question from the brief is real, narrow, and unhandled on the retry path).
- **Presence assert on shape drift:** present, probe4-calibrated, throws fail-closed; limitation (cannot see concept links) folded into F-01.
- **Recall ledger overflow:** bounded clear, tie-break-only degradation, 3 goldens, contract-documented. Correct and tested.
- **Eval harness when the server dies between seed and score:** exit 1 with clear message; scorecard written only after full scoring → no partial numbers ever published; re-seed idempotent; drift fails loudly with remediation. Correct.
- **verify-skills vs old code:** identity guard aborts before writes; strict `consolidated === false` check fails a pre-P1.2 server → exit 1, no false PASS. Correct.
- **§3 "searches never 500" with the new tie-break:** intact — new code is pure/non-throwing, all sources still wrapped in `runSource`; tested with stub stores in §O (no server needed).
- **QUERY_TIMEOUT_MS around the probe:** bounded 15s per send; residual latency/queue behavior → F-03.
- **Posture per new path:** search = degrade→signals (documented §3); writes = fail-closed (documented §3); merge-threshold config = fail-closed OFF (documented + goldens); ledger overflow = degrade tie-break (documented); harnesses = abort-before-write exit 1 (documented). Each path picks the right side — the gaps are documentation/evidence of two conditional failure modes, not wrong posture choices.

## Verdict Rationale

⚠️ **conditional** — the lane's failure posture is coherent and correctly chosen on every new path (writes fail closed, searches degrade, bad config fails safe, bounded ledger and bounded probe), the degradation contract of §3 survives the new tie-break, and both harnesses refuse to write to a wrong/old target. Two conditional-impact findings prevent an unqualified pass: **F-01** (writeBatch atomicity assumed-but-unverified on the merge path, with a non-healing retry interaction) and **F-02** (cross-key concurrent lost append reported as success, declared only in a code docstring — not in the contract source of truth). Both are Medium per the severity table (conditional impact), neither is exploitable or data-loss-at-scale in the documented single-process deployment, and both close with documentation/evidence work rather than rework.

- **COND-R1 (F-02):** promote the cross-key concurrent-survivor lost-append from the `store.ts` docstring into CONTRACT §3 (and README residuals) as a named residual with owner (engineering) and a tracking item — or serialize cross-key survivor merges — BEFORE this lane closes.
- **COND-R2 (F-01):** record writeBatch mid-batch atomicity for `updateMemoryContent` as an explicit §0 verified fact (probe evidence) or a declared assumption/residual with owner (engineering), including the stated consequence that concept links have no return var and the substring guard does not heal a partial commit.

F-03 and F-04 go to the backlog (owner: engineering) — they do not block this gate.
