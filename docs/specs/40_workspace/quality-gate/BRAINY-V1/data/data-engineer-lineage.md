## 3. TTL-as-mitigation trace (slot9 canary Note row)

Assuming a Note row past `BRAINY_TTL_DAYS` (set in env):

- (a) **Search (hybrid/BM25): SHOWN, not hidden, not deleted.** Hit `createdAt` arrives as `String(epoch-ms)` via `readString`; `Date.parse` → `NaN` → fail-toward-keep. `hidden = 0`, so no `ttl` signal either — silent pass-through. (Contrast: a Memory row with ISO `createdAt` is correctly hidden with signal.)
- (b) **Context/export (`/v1/context`, recap/handoff, sessions, note reads, MCP `brainy_reality_check`): SHOWN, always.** No `filterExpired` on any of these paths, independent of timestamp format.
- (c) **No TTL set (env absent): SHOWN, everything.** `ttlDaysFromEnv` → `undefined` → TTL OFF by declared design; all rows returned.
- (d) **TTL set: SHOWN anyway for Notes; hidden only for ISO Memory rows.** Same mechanism as (a). Nothing is ever deleted on any path — the sole deleter (`scripts/purge.ts`) iterates `listExpired` + `forgetMemory`, i.e. Memory rows exclusively.

**Honest residual:** for Note rows, TTL is neither hide nor delete on any path. A canary Note row persists indefinitely with zero code paths that remove it and zero paths that reliably suppress it. TTL is not a mitigation for DAT-002. Owner: engineering.
