## Rollback-point sanity check (plan §Rollback Points)

- **RP1 (concepts):** revert `src/concepts.ts` + `store.ts`/`embed.ts` hunks — no schema touched, verify.ts D-section restored. **Sanity: OK.** Note `tokenize` export is additive; revert is a pure code revert.
- **RP2 (dedup):** revert `db/queries.ts` + `store.ts` dedup hunks restores pre-dedup write path; `deduped` field removal is additive-reversible. **Caveat:** "index #8 dropped with `bootstrapIndexes` revert" is NOT backed by any drop mechanism in the repo (RK-002) — the index and written `dedupKey` properties persist as inert artifacts (probe3: server doesn't enforce uniqueness; missing property harmless). Behavior rollback still complete and fast (<15 min), but the stated *schema* rollback is partially inaccurate.
- **RP3 (lifecycle):** revert `search.ts`/`lifecycle.ts`/`purge.ts`; defaults OFF ⇒ no behavior change for unconfigured users mid-flight. **Sanity: OK** — for users who *did* set TTL/λ, revert re-exposes expired rows (expected, both directions observable, envelope signal disappears with it).
- **RP4 (hooks):** revert `capture.mjs` + plugin registration + `verify-capture.ts`; per-event exit-0 guarantee keeps host pipelines flowing. **Sanity: OK** — the `tool.execute.before` registration revert also removes RK-008(iii)'s silent POST.
- **Purge irreversibility:** deletions are one-way by feature design (no undo). Rollback of the *code* does not restore purged data — this is inherent, not a plan defect; guards (RK-001) are the mitigation. Plan's stated assumption "dev-instance data is seed/verify data, no production data risk" holds for the lane's own runs; it does **not** extend to future operators running `purge --all` against a production `HELIX_URL` (RK-001).
