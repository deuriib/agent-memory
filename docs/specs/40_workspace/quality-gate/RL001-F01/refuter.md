### Claim 2 — F-01 verify + ONE heal "closes the mid-batch atomicity assumption": **REFUTED (in part)**

- **Survived sub-claims:** heal cannot loop or double-append (RF-007); no error path returns success after a failed heal (RF-011); stale re-reads fail closed, never false-green (RF-008); exact-name linking is consistent end-to-end (RF-009); byte-identical content after the guard-path heal is unconditional (zero content writes) and reproduced live (RF-010); substring-guard heal provably non-appending (`f-01` byte checks green ×2 runs).
- **Refuted sub-claim:** the batch's `embedding` write escapes the verify entirely (RF-012/CE-001). `docs/CONTRACT.md:312` labels ATOMICITY **CLOSED** and `:325-326` says "its commit is DETECTED-and-healed app-side" — detection covers content/dedupKey/links only; a mid-batch partial commit that lands content but drops the `embedding` refresh passes all three invariants and leaves the vector index serving the pre-merge embedding (exactly the retrieval-defect class F-01 was opened for). The doc enumerates the three checked invariants honestly, so the *implementation* matches the enumerated list — but the **closure claim over-reaches**.

### Claim 3 — Test claims: **SURVIVED**

- TEST_MATRIX counts reproduced (RF-16); one scope caveat (F-6).
- Coverage gap (not a false test, but claimed behaviors with zero tests): expired-while-waiting fall-through, fresh-read fail-closed variants, and heal-still-violated→throw/content-drift-retry are exercised by NO test (RF-004/RF-005 + code audit of `src/store.ts:744-751`, `:850-868`, `:1029-1038`) → F-2.
